# وقتي — خطة التحديث الشامل (التصميم)

التاريخ: 2026-11-08 · المصدر: ملف «WAQTI — Enterprise System Modernization & Integration» + النظام المرجعي `attendance-main`.
القرارات المعتمدة: (1) القواعد أولًا ثم التصميم، (2) دمج الأجزاء المؤجلة (طلبات الراتب، إظهار/إخفاء شاشة الموظف، صلاحيات اللوحة) في هذه الخطة، (3) خصم التأخير: تناسبي + شرائح، مع تقريب وتاريخ سريان.

## 0. قيود ثابتة

- التطوير داخل وقتي نفسه: لوحة الإدارة (ES Modules) + تطبيق الموظف (React/Vite/TS) + Supabase. لا مشروع جديد، ولا إطار جديد.
- كل تغيير في القاعدة = migration + ROLLBACK + اختبارات محلية. **لا تطبيق على الإنتاج، ولا نشر، ولا push** إلا بموافقة صريحة لكل جزء.
- عزل الشركات وفحص الصلاحيات في الخادم دائمًا (`security definer` + `search_path=''` + فحص الشركة).
- لا حذف لبيانات تاريخية. الحذف = إيقاف منطقي (soft delete).
- كل مرحلة تُسلَّم وحدها: اختبارات تعمل فعلًا، ثم طلب «نعم».

## 1. ما يوجد الآن (التدقيق)

| المجال | الموجود في وقتي | الفجوة مقابل الملف |
|---|---|---|
| فترة السماح | phase12: بعد السماح تُحسب **كل** دقائق التأخير | الملف: تُحسب الدقائق **بعد** السماح فقط ← تعارض، ينتظر قرارك |
| التبرير | نوع إذن `late_arrival` بحد شهري؛ التطبيق يعرض النافذة إن بقي رصيد | الخادم يعتبر 09:05 «متأخرًا» (يتجاهل السماح) ← النافذة تظهر مبكرًا. الرصيد يُفحص في التطبيق فقط قبل العرض |
| الخصم | لا يوجد محرك خصم | مطلوب: سياسة لكل شركة (تناسبي/شرائح، تقريب، تاريخ سريان) |
| الإجازات | رصيد لكل سنة، إجازة من الإدارة، موعد الطلب، عطل رسمية — في أماكن متفرقة بالإعدادات | واجهة موحدة «الإجازات» |
| الأنواع | أنواع الإجازة ثابتة في الكود (6)، الطلبات `leave/permission/other`، أنواع الأذونات مرنة | أنواع إجازات/طلبات تُدار من اللوحة |
| الصلاحيات | «مدير النظام» = صلاحية كاملة | أدوار مخصصة + نطاق موظفين |
| التقارير | الحساب داخل `export.js` في المتصفح | محرك حساب واحد في الخادم + 3 تقارير |
| الواجهة | ألوان وخط النظام | هوية المرجع: Cairo + ألوان دلالية (تأخير/إضافي/غياب/معذور) |

## 2. المراحل

### المرحلة 1 — قواعد الحضور (التبرير، السماح، الخصم)

**1أ. حساب التأخير (قرار مطلوب):** إعداد لكل شركة `late_rule`:
- `all_after_grace` (الحالي): بعد السماح تُحسب كل الدقائق.
- `beyond_grace` (الملف): تُحسب الدقائق بعد السماح فقط.
الافتراضي يبقى الحالي حتى تغيّره الإدارة، لكي لا تتغير التقارير القديمة فجأة.

**1ب. نافذة التبرير:** تظهر فقط إذا: `تأخير خاضع للحساب > 0` و`رصيد التبريرات > 0` و`الموظف مؤهل`.
- الخادم يحسب «هل هو متأخر» مع السماح (إصلاح الخطأ الحالي).
- دالة خادم واحدة `employee_late_status()` بعد البصمة تعيد: التأخير الفعلي، السماح، الخاضع للخصم، الخصم المتوقع، الرصيد المتبقي، `offer: true/false`.
- عند نفاد الرصيد: لا نافذة. سطر معلومات فقط. البصمة لا تُمنع أبدًا.
- الإرسال يبقى محميًا في الخادم (قفل لكل موظف + فحص الحد) ضد الطلبات المتزامنة.

**1ج. محرك الخصم:** جدول `deduction_policies` لكل شركة:
- `kind`: `proportional` (كل X دقيقة = Y دقيقة خصم، مع التقريب: لأعلى/لأسفل/الأقرب) أو `tiers` (شرائح: من–إلى ← خصم ثابت).
- `effective_from` (تاريخ سريان)، والسياسة القديمة تبقى للأيام القديمة.
- دالة خادم واحدة `private.late_deduction(company, day, chargeable_minutes)`.
- الخصم لا يُعتبر نهائيًا قبل اكتمال الموافقات. التبرير المعتمد يلغي خصم تلك الدقائق.
- لوحة: الإعدادات ← الدوام ← «سياسة الخصم» مع معاينة (09:15 ← 0، 09:16 ← 12…).

### المرحلة 2 — الموظفون وأماكن العمل + زر التثبيت

- نافذة الموظف: إزالة «إضافة مكان» والحقل المرتبط؛ اختيار مكان موجود فقط.
- الإعدادات ← أماكن العمل: زر حذف + تأكيد. يُمنع الحذف إن ارتبط بموظفين نشطين (نعرض العدد وخيار «نقلهم إلى مكان آخر»). المكان المحذوف يُوقف منطقيًا (السجلات القديمة تبقى).
- «حذف الموظف»: نافذة تأكيد، اسم الموظف، كتابة الاسم لتفعيل الزر، فحص في الخادم، Audit. التنفيذ = `deleted_at` + إيقاف الحساب + فك الهاتف، ويختفي من القوائم، وتبقى سجلاته في التقارير.
- تطبيق الموظف: زر «تثبيت التطبيق» في الأعلى (`beforeinstallprompt` / `appinstalled`؛ تعليمات للآيفون؛ يختفي داخل التطبيق المثبت).

### المرحلة 3 — تنظيم اللوحة

- تبويب جديد **«لوحة المتابعة»**: اليوم افتراضيًا أو فترة بين تاريخين، وفلاتر (موظف، قسم، حالة). المؤشرات: المشمولون، الحاضرون (عدد فريد)، ساعات العمل، الغياب المثبت مقابل السجلات الناقصة، الإجازات حسب النوع، لم يسجلوا الحضور، نسيان الانصراف (بعد مهلة الانصراف فقط)، الطلبات حسب الحالة والنوع، التأخير (العدد والمدة)، الخروج المبكر. الضغط على مؤشر يفتح القائمة. تُحسب في الخادم بدالة واحدة مع فهارس.
- تبويب **«الإجازات»**: تبويبات فرعية: الطلبات، الأرصدة، أنواع الإجازات، العطل الرسمية، إجازة من الإدارة، موعد الطلب، السياسات. نقل فقط، والوظائف نفسها.

### المرحلة 4 — إعادة التصميم

- لوحة الإدارة: tokens جديدة (Cairo محليًا من المرجع، لون العلامة، ألوان دلالية: تأخير/إضافي/غياب/معذور)، بطاقات وجداول ونماذج ونوافذ موحدة، تنقل بالفئات، متجاوبة من 360px إلى الشاشات الكبيرة. يُعاد استخدام اختبار الشاشات الحالي (`layout.mjs`) على كل المقاسات.
- تطبيق الموظف: نفس الهوية، مع إبقاء زر البصمة العائم والتدفقات كما هي.

### المرحلة 5 — الإعدادات المرنة والصلاحيات (يدمج الأجزاء 3، 4، 5)

- **أنواع الإجازات** `leave_types` لكل شركة: الاسم، الوصف، الاستحقاق السنوي، مدفوعة/لا، يُخصم من رصيد/لا، مسار الموافقة، مفعّل/موقوف. الأنواع الستة الحالية تُنقل كبيانات بنفس المعرّفات، لكي تبقى السجلات القديمة صحيحة.
- **أنواع الطلبات** `request_types`: كل نوع مبني على «صنف» يدعمه المحرك (`leave`، `permission`، `other`، `financial`) مع حقول مختارة من قائمة مدعومة (تاريخ، فترة، وقت، مبلغ، ملاحظة، مرفق)، وقواعد تحقق، وتكرار مسموح، ومسار موافقة. **طلبات الراتب** (دفعة بنسبة، راتب كامل، مرات في السنة: مدة من آخر طلب أو فترات ثابتة) = صنف `financial`. لا تنفيذ لكود حر من الإعدادات.
- **المسميات والسلم الإداري**: `positions` (مسمى وظيفي) و`org_levels` (مستويات وتبعية) مع منع الحلقات، وربط بالموظف والقسم.
- **الأدوار** `admin_roles`: صلاحيات (قراءة/إضافة/تعديل/موافقة/إلغاء/حذف) لكل مجال، ونطاق (الكل / قسم / مكان). كل دالة `admin_*` تفحص `require_permission(مجال، فعل، موظف)` في الخادم. الدور منفصل عن المسمى. مدير النظام الحالي = دور «كامل» تلقائيًا (لا تغيير لمن يعمل الآن).
- **شاشة الموظف**: إظهار/إخفاء كل قسم وكل نوع طلب، للشركة مع استثناء لموظف.
- الأنواع الجديدة تظهر تلقائيًا في النماذج والفلاتر والتقارير. تعطيل نوع لا يكسر السجلات القديمة.

### المرحلة 6 — محرك التقارير

- دالة خادم واحدة لـ«حقائق اليوم» لكل موظف (مصدر الحقيقة الوحيد): الجدول الفردي، الإجازات، العطل، الاستثناءات المعتمدة، المناوبات بعد منتصف الليل، المنطقة الزمنية الواحدة. لوحة المتابعة والتقارير وExcel تقرأ منها، فلا حساب مكرر.
- تقارير: **ملخص** (أيام/ساعات، حضور، غياب، تأخير، خروج مبكر، إجازات حسب النوع، أذونات، استثناءات، نسبة الالتزام)، **تفصيلي** (حركات اليوم ومدتها واعتمادها والخصم)، **تحليل الحركات** (عدد ومدة كل حركة، معتمد/غير معتمد).
- اختبار مطابقة: إجماليات Excel = إجماليات التقرير.

### المرحلة 7 — التنظيف والتحقق والتوثيق

- إزالة الكود الميت بأدوات (`knip` للتطبيق، وفحص الاستيراد في اللوحة)، والتحقق قبل كل حذف، مع إبقاء ما يُستدعى ديناميكيًا.
- CHANGELOG، تعليمات التشغيل المحلي، نتائج الاختبارات.

## 3. الأمان

- كل جدول جديد: RLS مفعّل، ولا وصول مباشر من التطبيق، والوصول عبر دوال تفحص الشركة والصلاحية.
- كل تعديل إداري يُسجّل في `audit_log`.
- migrations غير هدّامة: إضافة أعمدة/جداول، ونقل البيانات مع الإبقاء على القديم حتى يثبت الجديد.

## 4. الاختبارات (لكل مرحلة)

- قاعدة البيانات: ملف اختبار لكل migration + الحالات الحدية (09:15 / 09:16، نفاد الرصيد، طلبان متزامنان، حذف مكان مرتبط/غير مرتبط، الاسم الخطأ في الحذف، عزل شركتين) + mutants + ROLLBACK ذهابًا وإيابًا.
- التطبيق: vitest + Playwright (وضع mock) على الهاتف.
- اللوحة: unit + behavior + layout على 6 مقاسات.
- لا يُعتبر شيء ناجحًا دون تشغيل فعلي.

## 5. مخاطر

- المرحلة 5 تلمس كل الدوال الإدارية (صلاحيات) وتغيّر طريقة تخزين الأنواع ← أكبر مخاطرة؛ تُنفذ على دفعات صغيرة مع إبقاء التوافق.
- تغيير قاعدة السماح يغيّر أرقام التقارير ← إعداد صريح، والافتراضي = الحالي.
- خطة Supabase المجانية بلا نسخ احتياطي ← يُنصح بنسخة قبل كل تطبيق على الإنتاج.
